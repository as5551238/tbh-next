## 1. 真运行率 (True Run Rate, TRR)

### 定义
产品核心功能中，用户可在浏览器中完成端到端操作闭环且数据持久化的比例。

### 公式

```
TRR = N_passed / N_total × 100%

其中：
- N_total = 核心功能检查点总数
- N_passed = 通过DDoD六条的检查点数
```

### 核心功能检查点枚举（当前基线 N_total = 60）

| 模块 | 关键操作（5个/模块） | 通过状态 |
|-------|----------------------|----------|
| Tasks | 创建/查看/编辑/删除/状态切换 | ☐☐☐☐☐ |
| Goals/OKR | 创建目标/添加KR/更新进度/删除/关联项目 | ☐☐☐☐☐ |
| AI Chat/Agent | 发送消息/收到回复/Agent执行/历史查看/设置配置 | ☐☐☐☐☐ |
| Review/Retro | 发起复盘/填写各阶段/AI草稿/导出/关闭 | ☐☐☐☐☐ |
| Risk Engine | 创建风险/评估/快照查看/预警/迁移数据 | ☐☐☐☐☐ |
| Projects | 创建/查看/编辑/删除/成员管理 | ☐☐☐☐☐ |
| DSTE Seasons | 创建赛季/关联目标/进度追踪/关闭/双写同步 | ☐☐☐☐☐ |
| Knowledge/OSP | 浏览市场/安装/查看内容/卸载/搜索 | ☐☐☐☐☐ |
| Templates | 创建/浏览/应用/编辑/删除 | ☐☐☐☐☐ |
| Weekly Report | 生成/AI辅助/编辑/导出/双写同步 | ☐☐☐☐☐ |
| Permissions | 角色分配/模块权限/视图切换/团队管理/邀请 | ☐☐☐☐☐ |
| Subscription | 查看计划/选择/状态查询/功能访问/降级 | ☐☐☐☐☐ |

### DDoD六条判定标准（单个检查点通过条件）

1. **代码存在**：对应功能的源码文件存在且被import使用
2. **构建通过**：`pnpm build`无该功能相关错误
3. **CRUD可执行**：对应操作在浏览器中可点击执行，无JS报错
4. **数据持久化**：操作后Supabase表有对应记录，刷新页面后数据仍在
5. **端到端闭环**：从入口导航到操作完成的完整路径可走通
6. **无运行时异常**：操作过程中控制台无error级别日志

### 阈值体系

| TRR范围 | 状态 | 行动 |
|---------|------|------|
| ≥60% | 绿 | 允许新增功能（受DR-88约束） |
| 40%-59% | 黄 | 冻结新功能，全部资源用于提升已有功能 |
| <40% | 红 | 触发8D-D4根因分析 + 用户决策（继续/转型/止损） |

### 当前基线

**TRR = 15%**（2026-06-12测算，9/60检查点通过）

## 2. Token预算 (Token Budget)

### 定义
单次迭代/会话中，可用于各类开发活动的token消耗上限及分配比例。

### 公式

```
Token预算比 = T_new / (T_new + T_improve) × 100%

其中：
- T_new = 用于"新增功能开发"的token消耗（含编码/测试/调试）
- T_improve = 用于"提升已有功能端到端可用性"的token消耗（含修复/优化/补全）
```

### 预算约束

| 真运行率 | 新功能预算上限 | 已有功能改进预算下限 |
|----------|---------------|---------------------|
| ≥60% | ≤20% | ≥80% |
| 40%-59% | 0% | 100% |
| <40% | 0% | 100% + 8D-D4 |

### 计量方式

- Agent每次工具调用后，flow-guardian自动累计分类：
  - 新增文件/函数/表 → T_new
  - 修改已有文件/修复bug/补充缺失逻辑 → T_improve
- 近似计算：工具调用次数 × 平均token/调用（按类型加权）

## 3. DDoD交付完成定义 (Definition of Done v2)

### 定义
一个功能"完成"必须同时满足的5个充要条件。

### 5条件（DR-47）

| 序号 | 条件 | 量化标准 | 验证方法 |
|------|------|----------|----------|
| 1 | 代码实现完整 | 所有CRUD操作有对应代码 | grep检查函数存在+被调用 |
| 2 | 构建零错误 | `pnpm build`返回exit 0 | CI执行 |
| 3 | 运行时可操作 | 浏览器中可完成端到端操作闭环 | 人工验证/自动化e2e测试 |
| 4 | 数据持久化 | Supabase表有记录且刷新后仍在 | 数据库查询验证 |
| 5 | 无遗留问题 | 无TODO/FIXME/console.error残留 | grep检查 |

### 判定逻辑

```
DDoD通过 = 条件1 AND 条件2 AND 条件3 AND 条件4 AND 条件5
DDoD率 = 通过DDoD的功能数 / 总功能数 × 100%
```

**注意**：条件1+2满足但3/4/5任一不满足 = **未完成**（这是过去最常见的幻觉完成模式）

## 4. 估算校准偏差率

### 公式

```
偏差率 = |实际工时 - 估算工时| / 估算工时 × 100%

缓冲系数计算：
- 有3+同类历史数据：缓冲系数 = max(1.3, 历史偏差率中位数)
- 有1-2条历史数据：缓冲系数 = 1.5
- 无历史数据：缓冲系数 = 2.0（必须标注"无校准数据"）
```

### 阈值

| 偏差率 | 状态 | 行动 |
|--------|------|------|
| ≤30% | 正常 | 继续执行 |
| 30%-50% | 注意 | 记录偏差原因 |
| 50%-100% | 告警 | 触发偏差分析报告 |
| >100% | 熔断 | 暂停执行+8D规划复盘 |

## 5. 生存力评分 (Survival Score)

### 公式

```
Survival = V×0.20 + G×0.20 + E×0.30 + I×0.15 + Im×0.15

其中：
- V (Value): 产品价值（1-10）— 用户痛点匹配度×付费意愿
- G (Growth): 增长势能（1-10）— 用户增长速度×留存率
- E (Execution): 执行效能（1-10）— 里程碑达成率×校准偏差率调整
- I (Innovation): 创新壁垒（1-10）— 技术独特性×竞品替代难度
- Im (Implementation): 实现质量（1-10）— TRR×代码质量×安全基线
```

### E维度的自动调整

```
E_adjusted = E_base - (平均偏差率 / 100) × 2

例：E_base=5, 平均偏差率150% → E_adjusted = 5 - 3 = 2
```

### 当前基线（2026-06-12）

**Survival = 4×0.20 + 2×0.20 + 3×0.30 + 2×0.15 + 5×0.15 = 0.8+0.4+0.9+0.3+0.75 = 3.15/10**
