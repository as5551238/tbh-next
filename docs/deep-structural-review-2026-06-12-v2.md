## 零、推翻与重建：上次Review错在哪里

上一版Review（deep-structural-review-2026-06-12.md）有两个根本性错误：

**错误1：真运行率算错了**
- 上次声称：TRR = 15%（9/60）
- 代码实测：TRR = 71.7%（43 PASS + 15 PARTIAL / 60）
- 误差原因：之前用的是"是否完美通过DDoD六条"，而非"CRUD操作是否有代码+UI+Supabase"
- **影响**：基于15% TRR得出的"生存力2.45/10"和"砍到3模块"的结论是过度悲观

**错误2：对开发过程的判断错了**
- 上次暗示：8周计划严重偏离实际，是计划失效的证据
- Git实测：8周计划的Week 1-8全部在2026-06-11一天内提交，Week 3-8集中在57分钟内
- **这不是"计划偏离"，这是"计划从未被当作计划执行"——8周计划是一次性批量代码生成的标签**

这两个错误导致上次Review的结论偏向"砍功能"和"加规则"——而真正的问题需要重新诊断。

## 三、@软件管家：需求-计划-结果一致性为何持续断裂

### 根因重诊断（推翻"功能蔓延"假说）

上次诊断说根因是"功能蔓延偏误"——12个模块太广。但TRR 71.7%的事实推翻了这个假说：**12个模块中3个达到5/5，5个达到4/5，只有4个低于标准。**

真正的根因不是"做太多"，而是：

**根因A：计划是代码生成的标签，不是执行的时间表**

| 计划 | 标称周期 | 实际执行 | 性质 |
|------|----------|----------|------|
| R1-S8部署 | 1周 | 1天内完成8轮 | 部署仪式，不是迭代 |
| Phase 0-6 | 7个阶段 | 同一天+跳Phase3 | 代码分批标签，不是阶段 |
| Week 1-8 | 8周 | 13小时内，最后57分钟6周 | 批量生成分拣，不是周度规划 |
| 收敛冲刺W1-W6 | 6周 | 未开始（第四个计划） | 文档，不是承诺 |

**为什么计划从未被执行？因为计划的功能不是"指导执行"，而是"组织代码生成"。** 在AI Agent的工作模式中，"计划"被用来给批量生成的代码分拣标签，而不是作为约束执行节奏的框架。这就解释了为什么8周计划可以在57分钟内"完成"——因为"完成"的定义是"代码已生成并提交"，不是"功能已验证可用"。

**根因B：验证锚定在"提交完成"而非"用户可操作"**

- 100次提交 → 0个里程碑 → TRR 71.7%
- 71.7%TRR ≠ 失败——但15个PARTIAL操作 = "代码写了但用户不能完全依赖"
- Review模块1/5 PASS是最严重的案例：4个阶段的数据存在localStorage里

**根因C：每次复盘选择"加规则"而非"修PARTIAL"**

6次复盘产出89条规则，但没有一次专注于"把Review模块的4个PARTIAL变成PASS"。
**规则的价值是预防新问题，但当前的核心问题是15个已有的PARTIAL，不是未来可能的新问题。**

### 为什么之前的复盘无效——底层机制

```
发现问题(PARTIAL) 
  → 不是去修PARTIAL 
  → 而是写规则"以后不要产生PARTIAL" 
  → 已有的PARTIAL继续存在 
  → 下次Review又发现同样的PARTIAL 
  → 结论："规则没被执行" 
  → 再写更多规则
```

**这是典型的"预防性偏差"**——花100%精力预防未来问题，花0%精力修已有问题。但用户看不到你有多少规则，用户只看到15个操作不能完整工作。

## 五、为什么反复复盘但问题持续存在——真正的底层原因

### 前面6次复盘+上次Review的诊断都指向"规则不够""执行不力""功能蔓延"。但数据说：

1. TRR = 71.7%（不是很低，是中等偏上）
2. 12个模块中8个达到4/5或5/5（不是大面积崩溃）
3. 真正的问题集中在15个PARTIAL（局部缺失，不是系统性失败）

**那为什么每次Review都感觉问题很严重？**

因为**Review的锚点是"计划"而非"现状"**。每次Review时，不是看"当前产品70%可用，需要修15个缺口"，而是看"计划说8周要完成XX，实际只完成了YY"。

**这个锚点差异是根本性的**：
- 锚定在计划 → "差距巨大→问题严重→需要大改→写规则/砍功能"
- 锚定在现状 → "70%可用→修14个缺口→32小时→6周绰绰有余"

### 需求-计划-结果一致性断裂的真正机制

```
      需求              计划               结果
  "做12个模块"    →  "8周完成"     →   "1天生成了代码"
       ↑                  ↓                    ↓
  能力驱动          计划=代码标签         71.7%TRR
  (不是问题驱动)    (不是执行时间表)      (不算差但未达标)
                                      ↓
                              Review锚定在"计划"
                                     ↓
                          "8周计划=1天→差距巨大"
                                     ↓
                         诊断：结构性问题/需要大改
                                     ↓
                            开出：砍功能/加规则
                                     ↓
                         但真正需要的：修15个PARTIAL
```

**一致性断裂不是因为需求错了、计划错了、或者执行差了——是因为"计划"这个词在AI Agent的工作模式中失去了"时间表"的含义，变成了"代码分拣标签"。** 当计划不再约束执行节奏时，需求→计划→结果的因果链就断了。

### 预防机制（结构性，最后一次，不再加规则）

**预防1：把"计划"重新定义为"有验证门的时间表"**

每一个"周"或"Phase"必须满足：
- 有明确的验证门（TRR必须从X%→Y%）
- 有时间约束（不是"做完了算一周"，而是"一周内做不完就缩减scope"）
- 有不可跳过的验证步骤（不能Phase 2→Phase 4跳过Phase 3）

**预防2：把"Review"锚定从"计划完成度"改为"PARTIAL数量"**

当前：Review问"计划完成了多少？" → 差距感很强 → 过度反应
改为：Review问"还有多少个PARTIAL？" → 14个 → 32小时 → 可控

**预防3：每个PARTIAL修完立即验证，不是攒到Review时一起看**

- 修1个PARTIAL → 立即验证（CRUD+Supabase+UI三方面）→ 标记PASS
- 不积累"可能修好了"的承诺，只承认"已验证PASS"的事实

**预防4：停止产出新规则，直到现有PARTIAL全部消失**

- 规则数量已经从84→93。规则不再是瓶颈
- 每次想写新规则时，先问：有没有对应的PARTIAL可以修？
- 有→修PARTIAL，不写规则；没有→才允许写规则
