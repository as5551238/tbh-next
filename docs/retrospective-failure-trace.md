## 核心结论

**所有历史复盘措施失效的根因是同一件事：规则只写入了文档，从未嵌入执行路径。**

具体表现：
1. 规则存在 → 但Agent编码时不检查 → 规则形同虚设
2. 验证锚定在"代码存在" → 即使规则要求"运行时验证"，Agent仍按旧习惯标记完成
3. 每次Review新增规则 → 但旧规则执行率未追踪 → 规则越来越多，执行率越来越低

## 失效模式分类

### 模式A：规则写入文档但无执行路径（占60%）

- **特征**：规则写进verifiable-rules.md或MEMORY.md，但Agent执行时无任何自动检查
- **代表**：DR-13/DR-14(L0)、SYS-2/SYS-3/SYS-5(L0)
- **修复**：v2刚性阻断矩阵——每条规则必须有至少一个阻断点（Agent自检/flow-guardian/gatekeeper）

### 模式B：检查点存在但不阻断（占25%）

- **特征**：有CP检查点，但CP只是"建议"不是"阻断"——Agent可跳过继续执行
- **代表**：DR-12(L2)有验证义务但无阻断后果
- **修复**：CP-16(DR-89)为硬阻断——缺三件套=禁止编码

### 模式C：验证标准错误（占15%）

- **特征**：验证锚定在"代码存在+构建通过"而非"用户可操作"
- **代表**：所有DR-91之前的完成判定
- **修复**：DR-91验证锚定转移——gatekeeper D1≤6如果无运行时证据

## 教训提炼

1. **规则不嵌入执行路径 = 没写**。每条新规则必须回答：谁来检查？何时检查？违规后果是什么？
2. **L0级规则是负债不是资产**。21条L0规则占24%但执行率≈0%——它们给了"我们有规则"的幻觉，实际分散注意力
3. **Review数量与质量负相关**。6次Review产出89条规则，但规则越多Agent越不可能全部遵守——收敛比扩张重要
4. **代码修复有效，文档修复无效**。16项实测修复中9处代码修改至今有效，而同期新增的规则几乎全部未被自动执行
